# Load test — 2026-09-23

First measured run of the API. Numbers are from a Windows development laptop (Node 22, local
Postgres, local Redis), so absolute values are indicative only; the useful part is the
before/after comparison and the failure modes it exposed.

## Setup

- Tool: `autocannon` (`-c 100 -d 15`, plus one `-c 250` run), one URL at a time.
- Target: a dedicated API instance on port 5001 started with `JOBS_ENABLED=false`, `LOG_LEVEL=warn`
  and `GENERAL_RATE_LIMIT_PER_MINUTE=1000000` (so the baseline per-IP limiter does not throttle the
  test client; every other limiter stayed on).
- Data: the seed database (53 published listings, 38 categories, 8 stores).

## Results

| Endpoint | Before (req/s avg · p50 · p99) | After (req/s avg · p50 · p99) |
|---|---|---|
| `GET /advertisements?pageSize=20` (100 conn) | 56 · 1,029 ms · 3,176 ms | 127 · 462 ms · 4,676 ms* |
| `GET /advertisements/:slug` (100 conn) | 71 · 896 ms · 3,046 ms | 144 · 430 ms · 1,062 ms |
| `GET /advertisements?search=phone&sort=popular` (100 conn) | – | 362 · 156 ms · 458 ms |
| `GET /categories?withCounts=true` (100 conn) | 207 · 302 ms · 1,942 ms | (unchanged, already cached) |
| `GET /advertisements/hero` (100 conn) | 157 · 365 ms · 2,107 ms | (unchanged, already cached) |
| `GET /advertisements?pageSize=20&sort=popular` (250 conn) | 67 · 2,440 ms · 4,209 ms · 0 errors | 209 · 73 ms · 5,942 ms · **37 × HTTP 500*** |

\* The "after" p99 spikes and the 37 errors all happened at the moment the 45 s listing cache
expired: 100–250 concurrent misses recomputed the same query at once and exhausted the
Postgres pool (`timeout exceeded when trying to connect`, `DB_POOL_MAX=10`). This is the
thundering-herd pattern; it was fixed by request coalescing (see below) and re-measured — the
final numbers are appended at the end of this file.

## What changed between the two runs

1. **Listing pages cached** (`ads:list:*`, 45 s TTL, busted on every write that changes what
   buyers see: listing create/update/publish/archive/feature/unfeature, store suspension,
   plan activation, plan expiry).
2. **View counters batched** — the detail page did one `UPDATE … viewCount + 1` per request;
   it now does `HINCRBY` in Redis and the `view-counts` job flushes to Postgres every minute.
3. **Single-flight cache fill** — concurrent requests for the same expired key share one
   database query instead of each running it (`cache.service.getOrSet`).

## Reading the numbers

- Cached endpoints top out around 200–360 req/s on this laptop; the ceiling is CPU
  (JSON serialisation + gzip) and the single Node process, not the database. In production,
  run several instances behind the load balancer (the code is already stateless: Redis holds
  the cache, rate-limit counters and job locks).
- The connection pool is the first thing to size in production (`DB_POOL_MAX` per instance ×
  instances < Postgres `max_connections`).
- "500 concurrent users" is realistic for browsing traffic with the cache in place; checkout
  and payment paths were not load-tested (they depend on K-Pay).

## Verified alongside

- Redis cache hits/misses are now visible in the logs (`result: "hit" | "miss"`) and were
  observed on repeated category/listing requests.
- Login throttling works: the 21st failed login within 15 minutes returns `429` with
  `RateLimit-*` and `Retry-After` headers. (Before this session it silently never fired —
  the Redis store's script load failed at boot and the failure was cached forever; see the
  `selfHealingScript` note in `src/middlewares/rateLimiter.js`.)

## Final run (after single-flight coalescing)

| Endpoint | req/s avg · p50 · p99 · errors |
|---|---|
| `GET /advertisements?pageSize=20` (100 conn) | 273 · 188 ms · 756 ms · 0 |
| `GET /advertisements?pageSize=20&sort=popular` (250 conn) | 117 · 1,052 ms · 5,310 ms · **0** (was 37 × 500) |

Versus the very first run: listings went from 56 to 273 req/s at 100 connections and the
median from 1,029 ms to 188 ms; the pool-exhaustion errors at 250 connections are gone.
